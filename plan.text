Understanding What You Actually Have
You have 4 sheets = 4 stages of a sales pipeline:
Inquiries → (won?) → Won Orders
          → (lost?) → Lost Inquiries
          → (not relevant?) → Declined Inquiries
It's a classic funnel — everything starts as an Inquiry and moves to one of 3 outcomes. This is the core logic your entire system is built around.

Why PostgreSQL over MongoDB here? Because your data is structured and relational — inquiries link to won orders, clients repeat across sheets, references link records. SQL handles this perfectly.


Database Design
Clients ──────────────────────────────┐
Principals ───────────────────────────┤
                                       ↓
                                   Inquiries
                                   (master table)
                                       │
                    ┌──────────────────┼──────────────────┐
                    ↓                  ↓                   ↓
             Won Orders          Lost Inquiries      Declined Inquiries
             (extended data)     (status = lost)     (status = declined)
Key idea: All 4 sheets share a base — they're all inquiries at different stages. So instead of 4 separate tables, you have:

One inquiries table with a status field (Active / Won / Lost / Declined)
One won_orders table that extends an inquiry when it becomes a won deal
clients and principals as separate tables (avoid repeating names everywhere)

The "Never Falls" Part — Reliability Rules

Validation everywhere — no empty required fields, no wrong date formats
Soft delete — never truly delete a record, just hide it (you can always recover)
Audit log — every change is recorded with timestamp + user
Database backups — daily automated backup of PostgreSQL
Status transitions are controlled — you can't go from Declined → Won directly, must go back to Active first
Input is typed — dates are datepickers, numbers are number fields, statuses are dropdowns — no free text where it shouldn't be
